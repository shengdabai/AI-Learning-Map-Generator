MAP 02 / AGENT CONTROL PLANE

参数不是开关清单

它们是在 Claude Code 启动前声明一份运行契约：带什么上下文、能做什么、何时询问、投入多少、怎样交付结果。

核心隐喻：代理的运行策略面板 核对版本：Claude Code 2.1.220 资料日期：2026-07-29
01
Essence

本质：给代理设置初始边界

prompt 告诉 Claude “想做什么”；参数决定这次运行“处于什么制度下”。

claude 参数本质上是在配置一个有上下文、有能力、有预算、有权限的代理进程。
Without parameters

依赖项目和用户默认设置，适合日常交互，但边界可能只存在于隐含配置中。

Why parameters exist

让一次会话的关键策略可显式覆盖、可复现、可由脚本声明。

New possibility

同一代理可在探索、受控编辑、后台执行、结构化流水线等制度间切换。

02
World model

世界模型：一次运行的六个控制面

参数的真正对象不是“功能”，而是代理的运行状态。

上下文目录、会话、系统提示、设置来源
能力工具、MCP、插件、浏览器、agent
授权何时询问、允许什么、拒绝什么
算力模型、effort、轮次、预算
生命周期交互、打印、后台、续接、分叉
交付文本、JSON、流、schema、调试证据

Objects · 对象

session、prompt、tool、permission rule、model、workspace、config、output event。

Actors · 角色

你、Claude agent、子 agent、工具、MCP server、hooks、操作系统、CI。

State · 状态

新会话/续接/分叉；手动/计划/自动/绕过；前台/后台；交互/非交互。

Value · 价值

把“相信代理”改造成“声明边界、观察行为、验证结果”。

03
Concept map

概念地图：三层运行契约

最重要的不是参数数量，而是分清“上下文、行动策略、交付接口”。

Layer 1身份与上下文它是谁，记得什么，看见哪里

Session

-c 续接本目录最近会话；-r 选择特定会话；--fork-session 从历史分叉。

控制连续性，而不是能力

Scope

--add-dir 扩展可访问目录；-w 用 Git worktree 隔离工作现场。

可见范围与改动隔离不同

Instruction

--system-prompt 替换默认系统提示；--append-system-prompt 在默认提示后追加。

替换比追加更彻底，也更危险
Layer 2能力与治理能做什么，何时需要许可

Capability

--tools 决定内置工具是否可用；--disallowedTools 明确禁用匹配工具。

能力集合是外边界

Permission

--allowedTools 让匹配动作免提示；--permission-mode 决定整体询问策略。

“可用”不等于“免确认”

Extensions

--mcp-config、--plugin-dir、--agent 注入额外能力或角色。

扩展能力也扩大信任面
Layer 3资源与接口投入多少，如何进入与离开

Compute

--model 选择模型；--effort 选择思考投入；打印模式还能限制轮次与预算。

质量、速度、成本之间的契约

Lifecycle

默认交互；-p 一次性打印；--bg 后台运行。

选择人机协作节奏

Output contract

--output-format 决定文本/JSON/流；--json-schema 约束结构。

把自然语言接入机器流程

Decision map

决策地图：先决定制度，再启动代理

以下不是命令教程，而是专业人士启动前的判断顺序。

需要接着同一问题继续

Decision

Reason

只需分析，不允许改动

限制工具并选择 plan/manual 制度

Reason

从能力层收窄比口头提醒更可靠

Outcome

代理可观察与推理，但影响面受控

Situation

结果要进入自动化流水线

Decision

使用 print + JSON/stream + schema

Reason

机器需要稳定接口，不是终端排版

Outcome

输出可验证、可消费、可监控

Situation

任务复杂但边界清楚

Decision

提高 effort，设置预算/轮次止损

Reason

更多推理不应等于无限运行

Outcome

质量投入与失败成本同时可控

Situation

配置、hook 或插件导致异常

Decision

用 safe mode 建立干净基线

Reason

先区分 Claude 核心与自定义层

Outcome

缩小故障搜索空间

05
Search space expansion

搜索空间：参数背后的难题

初学者很少问

  • 能力边界与免确认规则有什么不同？
  • 会话连续性会不会带入过时假设？
  • 项目配置、用户配置与命令行覆盖谁优先？
  • 非交互运行如何证明没有静默忽略错误配置？

专家真正关心

  • 这次运行的 trust boundary 在哪里？
  • 输出是否有稳定 schema 与失败语义？
  • MCP、插件、hooks 扩大了哪些供应链风险？
  • 成本、轮次、后台恢复与取消如何治理？

下一步探索

  • permission rule syntax 与最小权限
  • settings source 的优先级
  • MCP 能力发现与严格配置
  • stream-json 事件模型与可观测性

定义精通的问题

  • 能否为任务选择恰当自治等级？
  • 能否区分对话分叉、文件隔离与历史分支？
  • 能否把 agent 运行变成可审计契约？
  • 能否判断何时应提升能力，何时应缩小能力？

07
Transferable principles

可迁移原则：所有 agent 都有这些控制面

第一性原理 稳定自治系统必须同时定义目标、可见范围、能力、授权、资源上限和验收接口。
可迁移方法 稳定最小权限、显式上下文、运行隔离、结构化输出、预算止损、先基线后排障。
实现细节 变化参数名、可选 permission mode、模型别名、背景 agent 行为、版本新增功能。
稳定知识 长期session 连续性、capability 与 permission 的区别、交互与非交互接口、配置优先级。
变化知识 常复核本机 claude --help、官方 CLI reference、组织策略与插件/MCP 版本。
08
Minimum mental model

最重要的 15 组参数概念

这是“什么时候想到它”的索引，不是让你背完整语法。

1 · 交互节奏

-p / --print：把对话变成一次性、可管道化调用。

2 · 会话连续性

-c 续最近；-r 选特定；--fork-session 另开历史分支。

3 · 会话可识别性

-n / --name：让长期任务可被人类识别和恢复。

4 · 文件现场隔离

-w / --worktree：为 Git 仓库创建独立工作现场。

5 · 权限制度

--permission-mode：在 manual、plan、acceptEdits、auto、dontAsk、bypassPermissions 之间选择。

6 · 可用能力

--tools：限制内置工具集合；这是“能不能”，不是“问不问”。

7 · 免确认白名单

--allowedTools：匹配的工具调用无需提示；不会自动成为唯一可用工具。

8 · 明确拒绝

--disallowedTools：禁止匹配工具；可用于补足 MCP 等能力边界。

9 · 额外目录

--add-dir：扩展可访问目录；相当于扩大数据与改动范围。

10 · 模型与投入

--model 选能力配置；--effort 选本次推理投入。

11 · 非交互止损

--max-turns 与 --max-budget-usd：为 print 模式设置资源上限。

12 · 输出契约

--output-format 选 text/json/stream-json；--json-schema 约束结构。

13 · 扩展面

--mcp-config、--strict-mcp-config、--plugin-dir 控制外部能力来源。

14 · 提示策略

--append-system-prompt 保留默认能力；--system-prompt 是整体替换。

15 · 故障隔离

--safe-mode 关闭自定义层建立基线；--debug/--verbose 增加证据。

高风险边界

--dangerously-skip-permissions 绕过所有权限提示。它不是“更强”，而是移除人机闸门；官方仅建议在无网络沙箱等严格隔离环境中使用。

09
Common misconceptions

常见误区：参数名容易制造的错觉

误区 1

--allowedTools 等于只允许这些工具。

“allowed” 容易被理解为能力白名单。

更好的模型：它主要控制免提示规则；用 --tools 限制内置能力集合。

误区 2

恢复 session 等于恢复文件现场。

对话记忆与工作区状态看起来同时连续。

更好的模型：session 管上下文，Git/worktree 管文件历史与隔离。

误区 3

提高 model/effort 总会得到更好结果。

推理投入常被误当成目标清晰度。

更好的模型：边界、上下文和验收不清时，更多算力只会更深入地跑偏。

误区 4

跳过权限只是省掉确认。

交互摩擦比影响半径更可见。

更好的模型：它删除了一层治理，只应由外部隔离补偿。

误区 5

--system-prompt 只是多加一句要求。

名称没有突出“替换默认提示”。

更好的模型：需要保留默认行为时，优先理解追加与整体替换的区别。

误区 6

参数表是长期稳定知识。

CLI 文档像静态手册。

更好的模型：控制面稳定，具体 flags 与 choices 必须按版本复核。
