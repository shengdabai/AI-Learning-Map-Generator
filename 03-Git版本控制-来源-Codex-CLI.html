Learning map 03 · Git

Git 不是“保存按钮”，而是可分叉、可合流的历史图

当 AI 替你操作 Git 时，你不必先背命令；你必须知道当前在哪条历史、哪些变化尚未记录、一次操作是在移动指针、创造提交，还是改写共享历史。

核心判断 文件是当前状态；commit 是不可变快照；branch 是会移动的名字；协作是多条历史之间的同步与整合。

01

本质：内容寻址的快照数据库 + 一张提交关系图

Git 用不可变对象记录内容和父子关系，再用可移动引用告诉你“哪一个提交现在叫 main、feature 或 HEAD”。

Git 本质上是管理项目历史分叉与合流的分布式状态系统，而不只是“撤销文件修改”的工具。

为什么存在

软件和知识资产会被多人并行修改。团队需要保留因果关系、比较差异、试验新路线，并在不依赖单一中央服务器的情况下交换历史。

解决的根本问题

谁在什么基础上做了什么改变？哪些改变应进入共享主线？如果两条路线同时改变同一语义，如何让人明确作出整合决策？

之前怎么做

复制“最终版-v7-真的最终版”文件夹、交换 patch，或依赖中心式版本控制。分支昂贵、离线能力弱，历史常与工作副本强绑定。

新可能

低成本分支、离线完整历史、并行 Agent worktree、精确审查、二分定位、可验证发布，以及任何节点之间的历史交换。

AI 时代的变化：AI 可以快速制造大量改动，Git 的价值因此上升：它把“生成速度”约束进可审查、可隔离、可回滚的变更单元。
02

世界模型：三个本地状态，一张历史图，多个远端视图

先看清“变化在哪一层”，再谈分支、同步或撤销。

Working tree
当前可见文件你与 AI 正在编辑的现实现场
未跟踪 / 已修改尚未进入下一次提交候选
Index
暂存快照“下一次 commit 准备记录什么”
选择边界把工作现场拆成有意义的变更单元
Repository
Commit快照 + 作者/时间/说明 + 父提交
Object database以内容标识存储 blob、tree、commit、tag
Refs / Branches指向提交的可移动名字
HEAD当前检出位置与下一次提交的落点
Network view
Remote另一个完整仓库的位置别名
Remote-tracking ref本地对远端分支上次所见位置的记录
Fetch / Push交换对象并更新允许移动的引用
修改工作树产生新状态，但历史未改变
选择Index 定义下一快照包含什么
记录Commit 固化快照并连接父历史
交换 / 整合Fetch、push、merge 或 rebase 协调多条历史

关键区别：Git 不是持续自动保存所有变化。它允许你从工作现场中选择一个有意义的状态，形成可命名、可解释、可交换的历史节点。

03

概念地图：内容层、历史层、协作层

同一个词常跨层使用。把层级分开，Git 的复杂度会骤降。

Layer 1
内容状态

Working tree编辑当前文件；目的是形成候选状态；与 index 和 HEAD 快照比较产生 diff。
Index选择下一快照；目的是分离“正在做”与“准备记录”；连接工作树和 commit。
Blob / Tree按内容存储文件与目录结构；目的是去重和完整快照；被 commit 引用。
Diff比较两个状态；目的是审查变化；不是独立历史对象。

Layer 2
历史结构

Commit记录快照与父关系；目的是建立可追溯历史；其 ID 来自内容。
Branch / Ref移动到最新 commit；目的是给一条开发路线命名；不是文件副本。
HEAD指示当前检出位置；目的是确定工作基线与下一提交落点。
Merge / Rebase整合历史；前者保留分叉并创建合流，后者在新基础上重放并生成新提交。

Layer 3
协作与发布

Remote命名另一个仓库；目的是交换历史；它不是“云端主仓库”的固有身份。
Fetch取得对象与远端视图；目的是先观察，不自动整合当前分支。
Pull取得并整合；目的是快速同步；具体使用 merge 或 rebase 取决于策略与配置。
Push / PR / Tag发布历史、发起审查、标记版本；把本地路线变成团队或交付契约。
冲突的真实含义：Git 无法替人判断两条变化的语义如何共存。冲突不是 Git “坏了”，而是系统把一个需要所有者决策的歧义显式交给你。
04

决策地图：历史应该如何变化

Git 决策的核心不是选命令，而是判断：要保留、整合、发布、撤销还是重写哪段历史。

Situation

AI 要开始一条独立、可能反复的实现路线

Decision

新建唯一分支；并发或高风险时使用独立 worktree

Reason

分支隔离历史，worktree 进一步隔离可写现场

Outcome

实验可丢弃、可比较、可单独审查

Situation

工作树混有多个目的不同的变化

Decision

按意图选择暂存，拆成原子 commits

Reason

commit 是解释和审查单元，不是定时存档

Outcome

历史可理解、可定位、可单独撤销

Situation

要先看看远端变化，但不想改变当前工作

Decision

先 fetch，再比较本地与 remote-tracking refs

Reason

获取信息与整合历史是两个不同动作

Outcome

先观察分歧，再选择 merge 或 rebase

Situation

功能分支需要并入共享主线

Decision

根据团队历史政策选择 merge、rebase 或 squash

Reason

三者表达不同的因果与审计结构

Outcome

主线既正确，也符合团队可读性约定

Situation

已发布的提交引入错误

Decision

优先创建反向变更，而不是改写共享历史

Reason

共享历史的 commit ID 已成为他人的基础

Outcome

修复可见、协作安全、审计完整

Situation

只在本地、尚未共享的 commits 需要整理

Decision

可以重写或重排历史，但先确认引用与工作树安全

Reason

未共享历史没有外部依赖，整理成本低

Outcome

提交叙事更清楚，不伤害协作者

05

搜索空间：历史背后还有哪些问题

真正掌握 Git，要从“命令能不能跑”走向“历史是否表达正确因果”。

初学者很少问

  • 为什么 Git 需要 index，而不是直接提交当前目录？
  • branch 为什么只是一个小指针，却能表示整条路线？
  • remote-tracking branch 是远端实时状态，还是本地上次所见？
  • “撤销”究竟是恢复文件、移动引用，还是创建反向提交？

专家真正关心

  • 提交边界是否对应单一意图，能否独立理解和回滚？
  • 历史重写会让哪些外部引用、CI 产物或协作者失效？
  • 合并策略是在保留真实开发过程，还是优化主线叙事？
  • 凭据、大文件、生成物和敏感数据是否进入了对象数据库？

下一步值得探索

  • 三棵树模型：HEAD、index、working tree 如何比较？
  • merge base 为什么决定三方合并的语义？
  • reflog、对象可达性与 garbage collection 如何影响恢复窗口？
  • 签名、tags、release 与供应链可验证性如何连接？

定义掌握上限

  • 能否只看提交图就解释项目真实因果关系？
  • 能否在不破坏未提交工作的前提下恢复任何误操作？
  • 能否为多 Agent 并发设计分支 / worktree / 集成策略？
  • 能否让发布产物可追溯到源码、依赖、测试与审批？
06

生态系统：Git 管历史，不包办协作治理

Git 提供对象、引用和传输；身份、审查、权限、CI 与发布由周边系统补齐。

上游 Upstream

文件系统、编辑器、CLI、AI Agent、代码生成器和开发决策。它们制造工作树变化；Git 不判断变化是否正确，只忠实记录你选择的状态。

替代 Alternatives

手工备份、云盘版本、中心式 VCS（如 Subversion）、面向大规模二进制资产的 Perforce，以及不同历史模型的 Mercurial / Jujutsu。

互补 Complements

GitHub / GitLab 承载协作与权限；PR / code review 承载决策；CI 承载验证；issue / ADR 承载意图；LFS、制品库和备份系统承载 Git 不擅长的对象。

下游 Downstream

构建、测试、部署、发布、审计与回滚。Commit ID 成为连接源码、产物、环境和事故记录的共同身份。

07

可迁移原则：从版本控制迁移到所有知识工作

Git 的价值观可以迁移到文档、数据、Prompt、设计和 Agent 工作流。

第一性原理

可验证历史需要不可变状态、明确身份和因果关系；协作需要让分歧显式，并在整合点做责任明确的决策。

可迁移方法论

小批次变更、原子提交、意图说明、隔离实验、先比较再整合、共享后不轻易改写、产物可追溯。

稳定知识

工作树、index、commit graph、refs、HEAD、branch、remote、fetch、merge base、冲突与可达性。

实现细节

具体命令选项、默认分支名、merge / rebase 配置、托管平台按钮、Hooks、凭据助手与平台文件规则。

易变知识

托管平台政策、默认保护规则、签名机制、AI review 功能、大文件限制和企业合规要求。

08

最小心智模型：只记住这 16 个概念

它们足以让你监督大多数 AI + Git 工作，并识别危险操作。

  1. SnapshotGit 记录项目状态快照，并复用未变化内容。
  2. Content address对象身份来自内容；内容或关系变化，ID 就变化。
  3. Working tree当前可见、可编辑、可能尚未记录的现场。
  4. Index下一次提交的候选快照，是意图选择层。
  5. Commit不可变快照与父关系构成历史节点。
  6. Commit graph历史是 DAG，不是单一时间线。
  7. Ref / Branch分支是指向 commit 的可移动名字。
  8. HEAD当前检出位置和下一提交的默认落点。
  9. Diff两个状态之间的比较视图，不是状态本身。
  10. Remote另一个仓库的别名，没有天然“主从”地位。
  11. Fetch获取对象并更新远端视图，不自动改变当前工作。
  12. Push发布对象并请求移动远端引用，可能被策略拒绝。
  13. Merge保留两条父历史并创建合流关系。
  14. Rebase在新基础上重放变化，生成身份不同的新提交。
  15. Conflict无法自动决定的语义整合点，需要所有者判断。
  16. Shared-history rule未共享历史可整理；已共享历史优先追加修复而非改写。
09

常见误区：从“文件备份”转向“历史关系”

理解对象与引用后，Git 最令人恐惧的部分会变成可解释的状态变化。

误解

分支是一份完整项目副本。

为什么

切换分支时工作区文件会变化。

更好模型

branch 只是指向 commit 的名字；工作树根据所指历史被重建。

误解

commit 就是“保存当前所有文件”。

为什么

界面常把 stage 与 commit 合并成一个按钮。

更好模型

commit 记录 index 的快照，不一定等于工作树全部状态；选择边界是 Git 的核心能力。

误解

pull 只是“下载最新代码”。

为什么

结果看起来像文件被更新。

更好模型

pull 通常包含 fetch 和历史整合，因此可能创建 merge、执行 rebase 或产生冲突。

误解

rebase 只是让历史更直，没有代价。

为什么

最终文件内容可能相同。

更好模型

rebase 创建新 commits，改变身份与因果基础；共享历史上的重写会让协作者分叉。

误解

只要进入 Git，就永远不会丢。

为什么

Git 常能从 reflog 恢复误操作。

更好模型

未提交内容、被清理对象、敏感数据和托管故障都有边界；版本控制不是备份、秘密扫描或制品库的替代。

误解

AI 生成的 commit 越多，历史越安全。

为什么

更多检查点看似更容易回退。

更好模型

安全来自有意图的原子边界与验证证据；噪声 commits 会隐藏因果，反而增加审查成本。

10

总结：真正的收益

Git 的终点不是“回到昨天”，而是让变化拥有身份、因果和协作边界。

我真正获得的不是一个更高级的保存与撤销工具，而是让人和 AI 能安全分叉、验证、合流并追溯每一次变化的历史系统。

首要三问：变化在哪层？当前 HEAD 在哪？历史是否已共享？ AI 分工：AI 操作，人决定提交边界与整合政策 完成闭环：diff + tests + commit graph
