01

本质：把一位通用 AI 工程师，实例化到你当前的目录

Essence

在终端敲下 claude 的那一刻，发生的不是"打开了一个聊天程序"。 发生的是：一个通用的、无状态的模型，被实例化成一个有具体身份的工作实体—— 它有工作目录、有文件读写能力、有可调用的工具、有权限边界、有既定的行为守则。 你在命令后面追加的每一个参数，都是在填这份实例化契约上的一栏。

?为什么会存在

模型本身只会读文本、吐文本。要让它真正干活，必须给它三样东西：一个上下文（你的代码和文件）、一双手（读写、执行命令）、一套约束（哪些能碰、哪些必须先问）。CLI 就是这三样东西的交付形式。

←之前人们怎么办

网页聊天框时代：模型看不见你的文件系统，跑不了命令，改不了磁盘。你只能人肉当搬运工——复制代码进去、复制答案出来、自己粘贴、自己运行、自己把报错再贴回去。人是 I/O 瓶颈。

→带来什么新可能

循环闭合了：模型能读到真实代码、真实运行结果、真实报错，于是能自己迭代。人从"搬运工"变成"发包方"——你的核心工作从描述细节，变成设定边界与验收标准。

关键转折：一旦 AI 有了手，"它能做什么"就不再是能力问题，而是治理问题。 这就是为什么 claude 的参数里，权限相关的部分比模型相关的部分还多。

从这个角度看，参数列表突然有了秩序。它们不是按功能随机堆砌的，而是在回答四个必须回答的问题—— 这四个问题构成了本页其余部分的骨架：

①记忆从哪来

这次会话是全新开始，还是接着昨天的？上下文与 prompt cache 保不保得住？

会话生命周期

②被允许做什么

每一步都要我点头，还是完全放手？哪些工具能用，哪些禁用？

权限边界

③用哪个大脑

这活值得用最贵最深的模型，还是随手一个便宜的就够？

模型与算力

④输出给谁看

结果是给人在终端读，还是给下一个程序解析？两者的形态和计费都不同。

交互模式

这四个维度之上还有一层——上下文注入：--add-dir 决定它能看见多大的世界， --append-system-prompt 决定它的性格与守则，--mcp-config 决定它能接上哪些外部工具。 这一层不属于"治理"，属于"塑形"：你不是在限制它，而是在定义它是谁。

02

世界模型：一次会话里到底有哪些东西在动

World Model

要建立心智模型，先把这个世界里的名词、角色、状态和流程拆开摆平。 参数之所以让人记不住，往往是因为不知道它在作用于哪个对象。

OObjects · 对象

  • 会话（session）：一段有 ID、可续、可回放的对话历史，落盘保存。
  • 上下文窗口：模型这一轮能"看见"的全部内容，稀缺且有限。
  • 工具（tools）：读写文件、执行命令、搜索、抓网页等具体能力。
  • 权限（permissions）：每次工具调用要不要先问你，作用于工具而非文件。
  • settings 分层：企业策略 / 命令行 / 项目 / 用户全局，层层叠加。
  • MCP server：外挂的工具提供方，把外部系统变成可调用的工具。

AActors · 角色

  • 你：目标设定者、边界设定者、最终验收人。
  • 模型：推理与工具调用的执行体，不同 --model 换的是这一位。
  • hooks：挂在生命周期节点上的脚本，可以拦截、注入、提醒，在模型之外强制执行规则。
  • subagents：被派出去的子实体，有自己的上下文窗口，做完只回报结论。

四者共存意味着：出了问题要先分清是谁做的——模型的判断、hook 的拦截，还是权限的拒绝。

SState · 状态

  • 会话历史：决定"它还记不记得"，也决定重开会话的代价。
  • prompt cache：前缀稳定时命中，直接决定长会话的成本和延迟。
  • 工作目录：它默认能看见的世界边界。
  • 权限模式：当前这次会话的放权档位，可在会话中途改变。

VValue · 价值

价值不在"它能写代码"，而在闭环：读真实文件 → 改 → 运行 → 看真实报错 → 再改。 这个环里没有人肉搬运，所以迭代速度只受模型速度限制，不受你打字速度限制。

而参数的价值，是让你能在不看着它的情况下，依然对这个循环有把握。

Workflow · 一次会话的生命线

启动 → 加载配置与 CLAUDE.md → 对话循环 → 工具调用（经过权限闸门）→ 落盘 → 会话保存

① 会话生命周期 · 记忆从哪来

↺-c / --continue

Entity：最近一次会话　Action：原地接续

Purpose：保住上下文，同时保住 prompt cache 的前缀。Relationship：和"随手开新窗口"是直接对立的两种习惯。

什么时候想到它：昨天的活今天接着干、刚不小心关了终端。这应该是你的默认反射，而不是想起来才用的技巧。

⇄-r / --resume

Entity：历史会话列表　Action：挑一个恢复

Purpose：当你并行开了好几条线，需要精确回到某一条时用。Relationship：-c 是"最近那个"，-r 是"我要挑"。

什么时候想到它：同时在跑三个项目，要回到其中一个。会话内的 /resume 是同一件事的另一个入口。

⌘/compact

把长对话压缩成摘要，换来上下文空间。代价是：缓存前缀被打断，且工具调用序列会被序列化成文本。在工具密集的会话里慎用。

∅/clear

清空上下文重新开始，但不换进程。适合"上一个任务结束、下一个任务完全无关"——比开新终端窗口省一次冷启动。

▶裸 claude

全新交互式会话。它的隐含成本是：CLAUDE.md、settings、所有规则都要重新完整加载一遍。这不是免费的。

② 权限边界 · 被允许做什么

这是整个参数体系里唯一"选错会有真实代价"的部分。它不是布尔开关，是一条连续光谱：

◀ 事事确认 · 你承担时间成本完全放权 · 你承担后果成本 ▶
plan
只读探索，先出方案不动手。连"读"都不改变世界。
陌生仓库、方案未定、想先看清楚再说
default
每个有副作用的工具调用都问你一次。最保守的可执行档。
生产仓库、客户资料、任何"改坏了很麻烦"的场景
acceptEdits
文件编辑自动放行，命令执行仍需确认。日常开发的甜点档。
自己的项目、改代码为主、不想被编辑确认打断
dontAsk
不再打断你，按既定规则放行。适合已经建立信任的工作流。
成熟的自动化流程、你已经知道它会做什么
bypassPermissions
跳过权限系统。别名参数直接叫 --dangerously-skip-permissions——名字里就写着 dangerously。
隔离沙盒、容器、worktree 里的一次性实验
读这条光谱的正确方式：向右移动省下的是你的注意力，付出的是后果的不可逆性。 这两者的兑换率取决于环境——在 git worktree 里 bypass 几乎零成本，在客户的生产仓库里 bypass 是灾难。 所以正确的问题不是"用哪档"，而是"这次的工作现场，允许我犯多大的错"。

✓--allowedTools

白名单式细粒度授权：只有列出的工具能用，其余一律拒绝。适合"我确切知道这个任务需要哪几样工具"的自动化场景——比档位更精确，也更可审计。

✕--disallowedTools

黑名单式排除：其余照常，但明确禁掉某几样。适合"整体放权、但绝不能碰某个东西"——比如放开编辑但禁掉网络访问。

这两个参数和 --permission-mode 是正交的：档位决定"要不要问"，名单决定"能不能用"。 高放权 + 严名单，往往比中等档位 + 无名单更安全，因为前者的边界是显式写下来的。

③ 模型与算力 · 用哪个大脑

◎--model

接受简称（sonnet / opus / haiku / fable）或完整 model id。Purpose：在成本和深度之间做一次显式权衡。

心智模型：这不是"换工具"，是换一位同事。治理合同的其余条款——权限、目录、输出格式——一条都没变。

haiku · 机械批量、频繁调用 sonnet · 日常开发默认 opus / fable · 架构、深度推理

↯--fallback-model

主模型不可用（过载、限流）时自动降级到备选。Purpose：让无人值守的任务不因为一次瞬时故障就整条挂掉。

什么时候想到它：写定时任务或 CI 流程时。交互式会话你自己会重试，自动化不会——它只会失败。

④ 交互模式 · 输出给谁消费

⌗-p / --print

Entity：一次性无头执行　Action：跑完即退，输出到 stdout

这是"程序调用 AI"的门：管道友好、可脚本化、是 CI 和定时任务的唯一入口。Relationship：它同时也是一条计费分界线——见下方警告。

{}--output-format

text 给人读，json 给程序解析，stream-json 给需要边跑边处理的流式消费者。

原则：输出格式跟着消费者走，不跟着你的习惯走。人在终端看就 text，下一步要 jq 就 json。

#--max-turns

给自动化上预算护栏：最多来回几轮就必须停。无人值守的循环没有这个参数，就等于没有刹车——失控的成本不是线性的，因为每轮都要重算历史。

👁--verbose

把中间过程都打出来。无头模式最大的问题是不可观测——出了问题你只看到一个失败的退出码。verbose 是最基础的可观测性手段。

⚠计费分界：-p 不吃订阅额度
生效日 2026-06-15

自 2026 年 6 月 15 日起，无头/程序化调用走独立的 API 计费桶—— claude -p、 Agent SDK、以及一切 headless 自动化，都不再消耗你的订阅额度，而是按 API 价格单独计费。

  • 交互式会话不受影响：你在终端里正常对话，仍然走订阅额度，一切照旧。
  • 定时任务要重新算账：launchd / cron / GitHub Actions 里每天跑的 claude -p，现在每一次都在真金白银地花钱。
  • 批量作业尤其危险：跑批 + 长上下文 + 多轮迭代，token 消耗是二次方增长的，因为每轮都要重算全量历史。
  • 可行的替代：机械性、可无人值守的批量任务，改派其他 CLI（如 Codex CLI）跑；把 Claude 留在需要它编排和验收的地方。
  • 务必配 --max-turns：这是你在计费桶上唯一的硬刹车。

这条规则改变的不只是账单，还有架构选择：以前"能自动化就自动化"是无脑正确的； 现在每一个自动化都要先问一句"这值不值这个钱，能不能换个便宜的执行体"。

⑤ 上下文注入 · 它是谁、它看得见什么

◱--add-dir

扩大 AI 可见的世界。默认它只看得见当前工作目录——这既是安全边界，也是能力边界。典型场景：前后端在两个仓库、要参考隔壁项目的实现、共享的设计文档在别处。

Σ--append-system-prompt / --system-prompt

改变它的"性格与守则"。append 是在既有守则后追加（保留默认行为），替换版是完全接管——后者威力大、风险也大，因为默认守则里包含了很多你没意识到的安全行为。

⚯--mcp-config

接入外部工具。MCP 让"AI 能做什么"从固定集合变成可扩展集合——公司内部 API、数据库、私有系统，都可以变成它的一个工具。代价：每个 MCP server 都占用上下文预算（工具描述要塞进 prompt），装太多会挤掉真正干活的空间。

⧉--settings 与配置分层

配置不是单一文件，是层层覆盖的栈。理解覆盖顺序比记住每个字段更重要——绝大多数"我明明配了怎么没生效"，根因都是被更高优先级的层覆盖了。

层级（优先级由高到低）位置典型用途
企业策略系统级托管策略文件组织不可绕过的硬约束，个人改不了
命令行参数你这次敲的 --xxx一次性覆盖，只对本次会话生效
项目配置.claude/settings.json随仓库走的团队约定，可提交进 git
用户全局~/.claude/settings.json你个人跨所有项目的默认偏好

隔离与并行

⊞--worktree

给这次会话一个独立的 git 工作区。它解决的是并行时代最典型的事故：两个 AI 会话同时改同一批文件，互相覆盖，谁也不知道发生了什么。

隔离还有第二个效果：它让高放权变得便宜。在一个独立 worktree 里 bypass 权限，最坏结果是删掉这个 worktree 重来；在主工作区做同样的事，代价完全不同。

⚙维护子命令 · 生态位

  • claude update — 升级到最新版本
  • claude doctor — 环境自检，装完或出怪问题时第一个跑
  • claude mcp — 管理 MCP server 的增删查
  • claude plugin — 管理插件与 marketplace

这些不是"参数"，是同一个二进制下的管理面。知道它们存在就够了，需要时问它自己。

04

决策地图：从场景反查参数

Decision Map

真实工作中你不会想"我该用哪个 flag"，你会想"我现在要干这件事"。 下面九张卡片是反向索引：从处境出发，到决策、理由、预期结果。

S1昨天的活今天接着干
决策claude -c，不要敲裸 claude
理由新会话意味着上下文归零、CLAUDE.md 与全部规则重新加载、prompt cache 前缀作废。这三样都不便宜，而且它们的代价是隐形的。
预期直接接着说"继续"就行，不用重新交代背景；长会话成本可降一大截。
S2要在脚本 / CI / 定时任务里调用
决策claude -p --output-format json --max-turns N，并先算一遍账
理由json 让下一个程序能可靠解析，max-turns 是失控时的硬刹车。但更重要的是：2026-06-15 起这条路走独立 API 计费桶，跑得越勤花得越多。
预期可管道、可审计、成本可预估。如果任务纯机械，认真考虑换个更便宜的 CLI 来执行。
S3高风险仓库，怕它误操作
决策--permission-mode plan 先看，确认方案后再切 default 动手
理由plan 档连"读"都不改变世界，适合摸清楚陌生代码；default 保证每个有副作用的动作都经过你点头。两步走比一步到位安全得多。
预期你先拿到一份方案再决定放不放权，而不是边跑边紧张。
S4想并行跑两个互不干扰的实验
决策每条线各起一个 --worktree 会话
理由并行最大的隐患不是速度，是互相覆盖——两个会话同时改同一个文件，最后谁赢是随机的。worktree 从文件系统层面消除这个可能。
预期两条线各自跑到底，好的那条合回去，坏的那条整个删掉，零污染。
S5简单批量任务，只是想省事
决策--model haiku（必要时配 --fallback-model）
理由批量重命名、格式转换、提取字段这类活，用最深的模型是纯浪费。模型选择是成本与深度的权衡，不是"越贵越好"。
预期同样的结果，明显更快更便宜；省下的额度留给真正需要推理的部分。
S6要接入公司内部工具或数据库
决策--mcp-config 挂上对应的 MCP server
理由MCP 把"外部系统"变成"它的一个工具"，比让它靠猜或靠你复制粘贴可靠得多。但注意每个 server 都吃上下文预算，按需挂，不要全家桶。
预期它能直接查真实数据，而不是根据你的描述编一个看起来对的答案。
S7前后端在两个不同的仓库
决策在主仓库启动，用 --add-dir 把另一个仓库纳进视野
理由默认工作目录既是安全边界也是认知边界。跨仓改接口时，它看不见另一半就只能猜字段名——而猜错的接口比不改还糟。
预期改接口时两边同步，类型对得上，不用你人肉传话。
S8某个项目需要固定的额外规则
决策写进项目的 .claude/settings.json 和 CLAUDE.md，而不是每次敲 --append-system-prompt
理由命令行参数是一次性的，配置文件是持久且随仓库走的。团队成员和未来的你都能自动继承。
预期规则一次写好长期生效；命令行留给真正临时的覆盖。
S9一次性实验，改坏了不心疼
决策--worktree + 高放权档位，两者必须成对
理由放权的风险大小取决于现场。在隔离沙盒里全速放权，是效率最优解；在主工作区做同样的事，是在赌运气。先建沙盒，再谈放权。
预期跑得飞快，失败了删掉重来，主线纹丝不动。
九张卡片的共同结构：先判断"这次的现场是什么"（生产还是沙盒、交互还是无人值守、连续还是全新）， 再从现场推出参数。先想现场，后想 flag——这个顺序反过来就是背手册，背完还是用不对。
05

搜索空间扩展：你还不知道该问什么

Search Space Expansion

一个领域的真正门槛，往往不在"答案难找"，而在"问题想不到"。 下面四组问题按认知阶段排列——从初学者的盲区，到决定天花板的那一类问题。

A初学者不会问的

  • 命令行参数和会话内的斜杠命令，是同一套东西的两个入口吗？（不是。前者签契约，后者改状态。）
  • settings 到底有几层，谁覆盖谁？为什么我改了没生效？
  • CLAUDE.md 是什么时候被读进去的？改了它当前会话会变吗？（不会，要新会话。）
  • "权限模式"管的是文件还是工具？（工具。这个区别决定了你怎么设白名单。）
  • -c 和重开一个终端窗口，除了省事还有什么区别？

B专家关心的

  • prompt cache 的命中条件是什么？哪些操作会打断前缀？（换模型、改 CLAUDE.md、加 MCP、compact，都会。）
  • 权限模式和 hooks 组合起来能表达什么？hook 能不能在高放权档位下依然硬拦某类操作？
  • 无头模式的可观测性怎么建——只有退出码时，怎么知道它是"做完了"还是"放弃了"？
  • MCP server 的工具描述占多少上下文？装 20 个 server 会不会挤掉真正的工作空间？
  • subagent 的上下文是独立的，那"派出去"和"自己做"的成本临界点在哪？

C下一步值得探索的

  • hooks：把规则从"模型自觉"变成"系统强制"。这是唯一能真正保证某件事不发生的机制。
  • subagents：并行扇出 + 上下文隔离。让主会话只拿结论，不被细节撑爆。
  • Agent SDK：不再是"用 CLI"，而是"把这套能力嵌进你自己的产品"。注意它同样落在独立计费桶。
  • 多 CLI 编排：不同模型族各干各擅长的，跨族互审能抓到单模型的盲区。

D决定上限的问题

下面这几个问题没有标准答案，但你怎么回答它们，直接决定你能把 AI 用到多深：

  • 如何设计"放权但可审计"的自动化？——既不用盯着，事后又能说清它做了什么、为什么。
  • 什么样的任务不应该交给 AI 循环，哪怕技术上完全可行？
  • 当 AI 一次 ship 一批改动时，你怎么避免理解债——代码在跑，但没人知道为什么这么写？
  • 验收的成本一旦超过自己做的成本，委派就不再划算。这条线在哪？
一个判断标准：如果你现在还在问"这个参数怎么写"，说明还在手册阶段； 如果你开始问"这个自动化值不值得存在、失控了我怎么发现"，说明已经进入治理阶段。 后面这类问题，才是 AI 替不了你的部分。
06

生态系统：这个命令的上下游、替代与搭档

Ecosystem

孤立地看一个 CLI，很容易高估它也低估它。放回生态里看，才知道它的边界在哪、 哪些事该交给它、哪些事该交给它旁边的东西。

flowchart LR U["你 / 终端 / shell"] --> CC["claude CLI"] API["Anthropic API 与模型"] --> CC SET["settings 分层 与 CLAUDE.md"] --> CC CC --> HK["hooks 生命周期脚本"] CC --> MCP["MCP server 生态"] CC --> SA["subagents 并行扇出"] CC --> FS["文件系统 与 git"] HK --> FS MCP --> EXT["外部系统 数据库 内部 API"] CC --> CI["CI 与定时任务 走 -p"] CI --> BILL["独立 API 计费桶"] GIT["git worktree"] --> CC TMUX["tmux 多会话编排"] --> CC LD["launchd 或 cron"] --> CI

↑Upstream · 它依赖什么

  • Anthropic API 与模型：真正的推理发生在这里，CLI 只是壳。模型不可用时 CLI 也就不可用——这是 --fallback-model 存在的理由。
  • 终端与 shell：它继承你的环境变量、PATH、当前目录。很多"它跑不起来"的问题根因在这里，尤其是版本管理器（nvm、pyenv）的懒加载导致 PATH 解析失败。
  • 配置分层：企业策略 / 命令行 / 项目 / 用户全局，启动时就已合并完成。

↓Downstream · 谁建立在它之上

  • hooks：挂在生命周期节点上的脚本。它们在模型之外强制执行规则——模型可以"忘记"守则，hook 不会。
  • MCP 生态：把任意外部系统变成可调用工具，是能力扩展的主通道。
  • CI 与定时任务：全部经由 -p 这道门，因此也全部落在独立计费桶里。
  • 多 agent 编排：subagents、worktree 并行、跨 CLI 协作，都建立在"一次会话 = 一个可治理实体"这个抽象上。

⇆Alternatives · 替代品与它们的取舍

  • 网页版 Claude：零配置、随处可用，但没有文件系统、没有工具、没有权限系统。适合思考和讨论，不适合动手。
  • 其他 coding CLI（Codex CLI、Gemini 系工具等）：形态相似，各有强项。跨模型族的价值在于抓盲区——同一族的模型倾向于犯同一类错，也倾向于认可自己的输出。
  • IDE 内的 AI 助手：交互更顺滑，但通常缺少可脚本化的无头入口，做不了无人值守的自动化。

选择的判据不是"哪个更强"，而是"这个任务需要哪种形态"：要不要动文件、要不要无人值守、要不要第二意见。

+Complements · 最佳搭档

  • git：AI 改动的撤销键。没有版本控制的放权是裸奔——这也是为什么高放权档位几乎总是和 git 一起出现。
  • git worktree：并行隔离的物理基础，让"放权"从赌博变成可控实验。
  • tmux：多会话共存与观察。人不可能同时盯三个终端，但可以随时切进去看。
  • launchd / cron：会话外定时。注意它触发的是 -p，也就是计费桶那一侧。
一句话概括生态位：claude 不是终点，是一个可被编排的执行单元。 它向上依赖模型和配置，向下产生真实副作用，横向和 git、worktree、其他 CLI 组成工作流。 参数的作用，就是在把它塞进这个工作流时，说清楚它这一次扮演什么角色。
07

可迁移原则：哪些结论换个工具依然成立

Transferable Principles

具体的 flag 名字会变，会被重命名、废弃、合并。但下面这几条第一性原理， 迁移到任何 agent 工具都成立——认识它们，比背住任何一份手册都值。

第一性原理

Ⅰ自由度：收益与风险同源

给 AI 的自由度越高，它能替你省下的注意力越多，同时它能造成的破坏也越大。 这不是两个可以分别调节的旋钮，是同一个旋钮。

因此正确的做法不是"找到安全的高放权"，而是先改变环境使风险变小（沙盒、worktree、版本控制），再放权。

Ⅱ上下文是稀缺资源

上下文窗口有限且昂贵。每一个塞进去的东西——MCP 工具描述、规则文件、历史对话——都在挤占真正干活的空间。

所以"装得越多越强"是错的。真正的技能是判断什么该常驻、什么该按需加载、什么根本不该进来。

Ⅲ人机接口与程序接口要分离

给人看的输出追求可读，给程序看的输出追求可解析，两者的最优形态互相冲突。

凡是想"一份输出两边都用"的设计，最后两边都不好用。先确定消费者是谁，再决定格式。

可迁移方法论

M1
最小权限起步，逐步放权
从保守档位开始，观察它实际会做什么，建立信任后再往光谱右边移。反过来（先全放开再往回收）你永远不知道该收到哪。
M2
会话连续性优先于"干净的新开始"
开新会话的心理成本为零，实际成本不为零：上下文归零、配置重载、缓存作废。除非任务真的不相关，否则接着上一个。
M3
输出格式跟着消费者走
下一步是人读就给人类格式，下一步是程序解析就给结构化格式。不要因为"json 看起来更专业"就默认用 json。
M4
先改环境，再改档位
想放权就先建沙盒。隔离是放权的前置条件，不是可选的补充措施。
M5
无人值守必配预算护栏
任何不看着它跑的东西，都必须有轮数上限、时间上限或失败次数上限。没有刹车的循环，成本是超线性增长的。
M6
写代码的不给自己打分
验收要么用可执行的硬判据（测试、构建、退出码），要么换一个独立的实体来审。同一个上下文里自我审查，几乎必然通过。
◆ 稳定 · 值得记住的
  • 四个治理维度本身：记忆、权限、大脑、汇报格式。任何 agent 工具都要回答这四个问题。
  • 权限是光谱不是开关：这个认知框架比任何具体档位名都持久。
  • 配置分层覆盖：几乎所有成熟工具都是这个结构，只是层数和位置不同。
  • 隔离是放权的前提：从 chroot 到容器到 worktree，这条原则几十年没变过。
  • 交互式与程序化是两种模式：不只是界面差异，是行为、成本、可观测性的整体差异。
◇ 易变 · 用时再查的
  • 具体 flag 名字：--permission-mode 的档位名、简称拼写，都可能调整。
  • 模型简称与 id：模型更新频率很高，写死在脚本里迟早会坏。
  • 计费规则：2026-06-15 这条分界线本身就是新增的，未来还会变。
  • 配置文件字段：settings.json 的具体键名随版本演进。
  • 子命令的组织方式：mcp、plugin 这类管理面重构过不止一次。
左右两栏的用法不同：左边的要内化成反射，右边的直接问它自己—— 敲 claude --help 或者在会话里问一句，比翻你三个月前存的笔记准确得多。 把记忆预算花在框架上，把查询交给工具，这本身就是 AI 时代的学习方式。
08

最小心智模型：只记这 14 条就够用

Minimum Viable Mental Model

按重要性排序。前 5 条覆盖日常九成场景，后面的是遇到具体处境时才需要唤起的。 如果只能记一条，记第一条。

01
参数 = 治理合同，不是功能开关
你不是在配置软件，你是在给一位 AI 同事写工作条款：记忆从哪来、能动什么、用哪个脑子、结果交给谁。
02
四个维度撑起全部参数
会话生命周期 / 权限边界 / 模型与算力 / 交互模式。第五个维度是上下文注入——那不是限制它，是定义它是谁。
03
-c 续会话应该是默认反射
开新会话是有代价的：上下文归零、配置重载、缓存前缀作废。只有任务真的不相关时才值得付这个价。
04
权限是一条光谱，不是布尔值
plan → default → acceptEdits → dontAsk → bypassPermissions。向右省注意力，向左省后果。选哪档取决于现场，不取决于心情。
05
-p 是"程序调用 AI"的门，也是计费分界
2026-06-15 起它走独立 API 计费桶，不吃订阅额度。交互式不受影响。设计自动化前先算这笔账。
06
模型选择 = 成本与深度的权衡
haiku 机械批量、sonnet 日常、opus/fable 深度推理。换模型是换同事，不是换工具——合同其余条款一条没变。
07
配置分层覆盖：企业 > 命令行 > 项目 > 全局
"我明明配了怎么没生效"，九成是被更高优先级的层盖住了。查问题先查覆盖顺序。
08
上下文来自工作目录 + CLAUDE.md + settings
这三样在启动时就已加载完成。改了 CLAUDE.md 当前会话不会变——要新会话才生效。
09
worktree = 并行隔离，也是放权的前置条件
同时跑两条线不互相覆盖；同时让高放权变得便宜——最坏结果只是删掉这个工作区。
10
命令行参数签契约，斜杠命令改状态
--permission-mode 在门口签，/compact /clear /resume 在屋里改。搞混了就会问出"为什么这个不能中途改"。
11
输出格式跟着消费者走
人读 text，程序解析 json，需要边跑边处理用 stream-json。不要因为"看起来专业"选格式。
12
白名单/黑名单与权限档位正交
档位决定"要不要问"，名单决定"能不能用"。高放权 + 严名单往往比中档 + 无名单更安全，因为边界是显式写下的。
13
上下文是稀缺资源，MCP 不是越多越好
每个 MCP server 的工具描述都要塞进 prompt。装满全家桶会挤掉真正干活的空间。
14
无人值守必须有刹车
--max-turns 加上 --fallback-model：前者防失控，后者防瞬时故障整条挂掉。自动化不会自己重试，也不会自己停。
09

常见误区：听起来对，但会让你走偏

Common Misconceptions

这六条不是"知识点错误"，是心智模型错误——它们不会立刻让你报错， 只会让你在几个月后发现自己一直在用一种笨办法。

✕「参数越多说明用得越高级，应该都学一遍。」
✓90% 的日常场景只需要 3-4 个：-c 续会话、一个合适的 --permission-mode、必要时 --model。剩下的属于"知道它存在，用时再查"。把记忆预算花在四个维度的框架上，而不是花在穷举 flag 上——框架能推出参数，参数推不出框架。
✕「bypassPermissions 只是省事，本质上没什么区别。」
✓它转移的是责任，不是消除风险。开着权限确认时，每次危险操作前系统会问你；关掉之后，同样的危险操作照做，只是没人问了。风险一分没少，只是从"系统帮你挡"变成"你自己记得"。唯一让 bypass 真正安全的方式，是先把环境变成沙盒——worktree、容器、可随时丢弃的副本。
✕「-p 和交互式只是界面差别，一个有对话框一个没有。」
✓差的是三样东西：计费（2026-06-15 起 -p 走独立 API 桶，不吃订阅额度）、行为模式（无头模式无法向你追问，遇到歧义只能自己拍板）、可观测性（交互式你全程看着，无头只有一个退出码）。把定时任务从交互习惯直接搬过去，账单和结果都可能出乎意料。
✕「换个 --model 等于换了个工具，得重新适应。」
✓只是换了个大脑，治理合同一条没变：权限档位、可见目录、输出格式、配置分层，全部原样生效。所以模型切换应该是一个轻量决策——这个任务够简单就 haiku，需要深推理就上更强的。怕换模型，本质是没建立"参数即合同"的心智模型。
✕「开个新窗口更干净，反正启动很快。」
✓"启动快"和"成本低"是两回事。新会话意味着：上下文归零（你要重新交代背景）、CLAUDE.md 与全部规则重新完整加载、prompt cache 前缀作废。前两项浪费你的时间，第三项直接浪费额度。"想换个干净的"是心理需求，不是技术需求——真正不相关的任务才值得开新会话。
✕「配置写在哪一层都一样，能生效就行。」
✓层级决定作用范围和寿命：命令行参数只管这一次，项目配置随仓库走并且团队共享，用户全局跨所有项目。把只该在某个项目生效的规则写进全局，会污染其他所有项目；把团队约定写成命令行参数，则每次都要重敲、别人也拿不到。选层级 = 选这条规则该活多久、该管多宽。
10

总结：你真正获得的是什么

Synthesis
我真正获得的不是一张参数速查表，
而是一套给 AI 雇员签工作合同的治理框架。

速查表会过期——flag 会改名、档位会重组、模型简称每季度都在变。 但"每次开工前，先想清楚这位同事的记忆从哪来、能动什么、用哪个脑子、把结果交给谁"， 这个动作不会过期。它在任何 agent 工具上都成立，在明年的工具上也成立。

①记忆

这位同事是新来的，还是接着昨天的活？-c / -r 决定你要不要重新交代一遍背景。

②权限

他能动什么、动之前要不要报备？光谱上的位置该由现场决定，不由心情决定。

③大脑

这活配得上多贵的脑子？成本与深度的权衡，每次都该显式做一遍。

④汇报格式

结果给人看还是给程序吃？这一条同时决定了形态、可观测性，以及账单落在哪个桶。

如果读者已经假设 AI 能替他完成绝大多数具体操作，那么参数的语法根本不值得背—— 忘了就问它自己，它答得比任何文档都快。值得投入注意力的只有一件事： 在把一件事交出去之前，把这四栏填清楚。

这也是为什么本页从头到尾没有做成手册。手册假设你需要"找到那个参数"； 而真实的困难从来不在找不到参数，在于不知道自己正在做一个治理决策—— 随手敲了个裸 claude，随手开了 bypass，随手把定时任务从交互习惯搬过去。 这三个"随手"，分别对应着浪费的上下文、转移的责任、和一张没预期的账单。

最后一个可迁移的判断：当你开始用"我要给它多大自由度、我怎么验收"来思考， 而不是"这个 flag 怎么写"，你就已经从工具使用者变成了工作流设计者。 前者的天花板是工具的能力，后者的天花板是你自己的判断力。
