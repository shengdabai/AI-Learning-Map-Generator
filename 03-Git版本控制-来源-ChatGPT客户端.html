MAP 03 / COLLABORATIVE HISTORY GRAPH

Git 不是云端备份

它把工作中的每次有意义变化组织成一张内容寻址的历史图，让人和 AI 能比较路线、审查证据、并行探索与安全回退。

核心隐喻：可协商的历史图 本机 Git：2.54.0 稳定度：数据模型高 / 平台流程中
01
Essence

本质：给变化建立身份与因果

Git 的关键不是“保存旧文件”，而是让每个项目状态有身份、每次演化有父子关系。

Git 本质上是一个内容寻址的快照图数据库，外加一套移动指针与交换历史的协作协议。
Before

复制“最终版-2-真的最终版”，共享文件夹互相覆盖，用邮件解释谁改了什么。

Why it exists

在分布式协作中，让历史可验证、路线可分叉、合并可讨论、失败可回退。

New possibility

人和多个 AI agent 可以在隔离路线中并行工作，再按证据集成。

02
World model

世界模型：从文件变化到共享历史

Git 管的不是“文件是否保存”，而是工作状态如何被选择、命名、连接与交换。

工作区此刻可见、可编辑的文件状态
索引下一次提交要包含的精确快照草案
Commit带作者、时间、父关系的不可变快照
Branch / Ref指向某条路线最新节点的可移动名字
Remote另一个仓库及其历史视图
Integration评审、合并、发布与回退

Objects · 对象

blob、tree、commit、tag、branch/ref、index、working tree、repository、remote。

Actors · 角色

作者、审阅者、AI agent、CI、托管平台、发布系统、未来的维护者。

State · 状态

未跟踪、已修改、已暂存、已提交、已共享、已集成、已发布、已回退。

Value · 价值

可比较、可归因、可并行、可审查、可恢复，以及让变化成为协作对象。

03
Concept map

概念地图：对象、指针与协作

Git 最难的部分，往往来自把三个层次混在一起。

Layer 1内容对象不可变的事实

Blob / Tree

实体：文件内容与目录结构。动作：按内容计算身份。目的：复用与验证。

快照的物质基础

Commit

实体：tree + 元数据 + 父提交。动作：固化状态。目的：建立因果节点。

保存的是项目快照，不只是 diff

Graph

实体：由 parent 连接的 DAG。动作：表达分叉与汇合。目的：保存演化关系。

历史不是直线，而是有向图
Layer 2工作与命名当前在做什么、哪条路线叫什么

Working tree

实体：可编辑文件。动作：试验与修改。目的：承载尚未定案的工作。

现实现场，不等于历史

Index

实体：下一快照的草案。动作：选择变更。目的：定义提交边界。

把“我改了”变成“这次要讲什么”

Ref / Branch

实体：指向 commit 的名字。动作：随新提交移动。目的：命名一条工作路线。

分支很轻，因为它主要是指针
Layer 3同步与协商不同仓库如何交换与整合事实

Remote

实体：另一个 Git 仓库。动作：获取与发布对象。目的：分布式协作。

GitHub 是托管平台，不是 Git 本身

Merge / Rebase

实体：两条历史关系。动作：汇合或重述。目的：形成可理解的集成历史。

都处理关系，语义不同

Review / CI

实体：差异、检查、讨论。动作：验证与批准。目的：让共享历史获得信任。

Git 提供证据，团队决定政策
04
Decision map

决策地图：专业人士何时想到 Git

核心判断是：这次变化需要怎样的隔离、证据、共享与恢复。

Situation

准备开始一条独立改动路线

Decision

建立清晰分支；并发时隔离 worktree

Reason

路线身份与文件现场都需独立

Outcome

实验互不覆盖，易比较与集成

Situation

工作中混入多种不相关变化

Decision

按意图选择提交边界

Reason

commit 应表达一个可审查主张

Outcome

未来可理解、可回退、可复用

Situation

需要并入他人或 AI 的路线

Decision

先审查差异和测试，再整合历史

Reason

合并是信任决策，不是机械同步

Outcome

共享分支只接收有证据的变化

Situation

共享历史中的改动需要撤销

Decision

优先新增反向变化，而非改写已共享事实

Reason

他人可能已经基于旧节点工作

Outcome

历史诚实，协作者可安全同步

Situation

本地私有路线杂乱、尚未共享

Decision

在共享前整理叙事

Reason

私有历史可塑，共享历史是公共接口

Outcome

审查者看到清晰因果而非操作噪声

05
Search space expansion

搜索空间：从“怎么提交”走向“如何治理变化”

初学者很少问

  • 一次 commit 在向未来维护者主张什么？
  • 工作区、索引、HEAD 各代表哪个世界？
  • 为什么远程分支只是本地记录的远端视图？
  • 冲突是文本问题，还是意图问题？

专家真正关心

  • 历史是否能支持审计与故障定位？
  • 分支策略是否匹配发布与风险模型？
  • 哪些历史可以重写，哪些已经成为公共契约？
  • CI 验证的是 commit，还是漂移中的环境？

下一步探索

  • 内容寻址与对象存储
  • 三路合并与冲突语义
  • worktree、submodule、monorepo 的边界
  • 签名、供应链与 provenance

定义精通的问题

  • 能否设计既支持并行又限制集成风险的流程？
  • 能否从历史图恢复一次决策的因果？
  • 能否在不破坏公共历史的前提下修复错误？
  • 能否让 AI 的每次改动都可归因、可验证、可回退？

07
Transferable principles

可迁移原则：历史是团队的接口

第一性原理 稳定不可变事实 + 可移动名字 + 显式关系，能同时支持验证、分叉与汇合。
可迁移方法 稳定按意图切分变化、隔离并行现场、共享前审查、公共历史追加修复、用自动检查保护集成点。
实现细节 变化托管平台菜单、默认分支名、merge queue、保护规则、某个团队的分支策略。
稳定知识 长期对象、commit DAG、ref、index、working tree、remote、三路合并、公共与私有历史。
变化知识 常复核Git 版本行为、平台权限、CI 配置、签名与供应链政策、组织发布流程。

09
Common misconceptions

常见误区：文件思维遮住了图思维

误区 1

Git 保存的是一串文件差异。

界面最常展示 diff。

更好的模型：commit 指向完整项目快照，diff 是两个快照的比较结果。

误区 2

Branch 是文件夹副本。

传统“复制目录”经验很强。

更好的模型：branch 主要是指向 commit 的轻量可移动引用。

误区 3

GitHub 就是 Git。

多数人从托管平台界面第一次接触 Git。

更好的模型：Git 是分布式版本模型；GitHub 是围绕它构建的协作平台。

误区 4

Git 就是备份。

它确实能找回历史版本。

更好的模型：Git 保护已记录历史；未提交文件、凭据与仓库灾难仍需要其他保护。

误区 5

冲突说明 Git 出错。

系统无法自动选择让人感觉像故障。

更好的模型：冲突是两种意图无法自动合成，需要人或 AI 明确语义。

误区 6

有 AI 后 commit 可以随便写。

AI 能快速总结 diff。

更好的模型：提交边界是协作与回退单位，仍需由目标与验证定义。
